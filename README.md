# Solin — شبیه‌ساز معاملاتی BTCUSDT و بک‌تست قابل‌بازتولید

> **این نسخه فقط Paper است. معاملهٔ واقعی، حتی با کلید صرافی یا فایل تأیید قدیمی، قابل فعال‌کردن نیست.**
> مسیر Live قبلی حفاظت و بازیابی قابل اتکا نداشت. آن را تا زمان پیاده‌سازی و آزمایش مستقلِ reconciliation، fill و stop سمت صرافی مسدود کرده‌ایم، نه اینکه آمادهٔ استفادهٔ واقعی اعلام کنیم.

## چه چیزی تغییر کرده است؟

- کلاینت فقط دو endpoint عمومی خواندنی را می‌پذیرد؛ امضا/سفارش/اهرم/حساب واقعی مسدود است. هیچ کلید صرافی لازم نیست.
- داشبورد احراز هویت دارد، بدون رمز امن پاسخ ۵۰۳ می‌دهد، فقط داده می‌خواند و دیگر به کلید صرافی یا script خارجی نیاز ندارد.
- وضعیت Paper، سرمایه، پوزیشن، شمارش مدت معامله، pending signal و اندیکاتورها به‌صورت تراکنشی در SQLite ذخیره می‌شوند. checkpoint و دفتر رویدادها با هم commit می‌شوند.
- قفل تک‌نویسنده، کنترل revision، بازیابی دقیق و جلوگیری از پردازش تکراری کندل اضافه شده است.
- کندل ناقص وارد موتور نمی‌شود؛ gapها کامل دریافت یا رد می‌شوند. هیچ کندلی یا Order Flow جعلی ساخته نمی‌شود.
- حجم معامله از تنظیم ریسک واقعی، فاصلهٔ stop، هزینه و سقف notional محاسبه می‌شود. PnL بر اساس مقدار و fill شبیه‌سازی‌شده است؛ Short فرمول معکوس ندارد و زیان به R مصنوعی محدود نمی‌شود.
- stop قبلی قبل از تریلینگ جدید بررسی می‌شود؛ stop جدید از کندل بعد معتبر است. خروج زمانی مستقل از طول حافظه است.
- Circuit Breaker فقط ورود جدید را می‌بندد، نه مدیریت معاملهٔ موجود. مبنای روز UTC و سرمایهٔ ابتدای روز است؛ پس از فعال‌شدن تا روز بعد قفل می‌ماند.
- واحد درصد در API/داشبورد یکسان شده؛ heartbeat تازه با خطای بات یا بازار کهنه به‌عنوان وضعیت سالم نمایش داده نمی‌شود.

## معماری کوچک و مشترک

```text
CoinEx public data / historical CSV
                |
        validated closed candles
                |
       streaming StrategyEngine
                |
        next-bar pending signal
                |
        TradingSession + RiskManager
                |
        PaperBroker: quantity / fill / fee / funding / position
                |
        SQLite checkpoint + journal  --> authenticated read-only dashboard
```

همان `TradingSession` در polling و replay استفاده می‌شود. اندیکاتورها causal، دارای حافظهٔ محدود و قابل ذخیره هستند. این نسخه قرارداد اجرای اصلاح‌شده دارد؛ نباید آن را معادل بیت‌به‌بیتِ بک‌تست قدیمی ناموجود دانست.

## نصب توسعه

Python ۳.۱۱ و ۳.۱۲ هدف هستند؛ Linux برای قفل `flock` لازم است.

```bash
python3 -m venv .venv
.venv/bin/python -m pip install --require-hashes -r requirements-dev.txt
cp .env.example .env
chmod 600 .env
```

برای داشبورد یک رمز تصادفی بسازید و **فقط در `.env` محلی** به‌عنوان `DASHBOARD_PASSWORD` قرار دهید؛ رمز یا کلید را در چت، Git یا لاگ عمومی منتشر نکنید:

```bash
.venv/bin/python -c 'import secrets; print(secrets.token_urlsafe(32))'
```

کاربر داشبورد `admin` است. کلید CoinEx در این نسخه کاربردی ندارد و نباید به محیط این سرویس‌ها داده شود.

### اجرای محلی / Codespaces

```bash
# فقط یک polling عمومی؛ برای بررسی دسترسی شبکه و شروع Paper
.venv/bin/python bot.py --once

# اجرای ادامه‌دار Paper
.venv/bin/python bot.py

# ترمینال جدا: .env قبل از import برنامه توسط Uvicorn خوانده می‌شود
.venv/bin/uvicorn dashboard.server:app --env-file .env --host 0.0.0.0 --port 8000 --no-proxy-headers
```

پورت Codespaces را **Private** نگه دارید. اجرای native بالا را روی شبکهٔ عمومیِ بدون TLS منتشر نکنید؛ HTTP Basic بدون TLS محرمانه نیست. از HTTPS محیط توسعه، SSH tunnel یا reverse proxy دارای TLS و rate limit استفاده کنید. endpoint `/healthz` فقط زنده‌بودن پردازش داشبورد را می‌گوید و هیچ آمار حسابی نشان نمی‌دهد.

Polling به دسترسی HTTPS به CoinEx نیاز دارد. در محیط این بررسی اتصال مستقیم TLS به CoinEx/Binance برقرار نشد؛ اجرای شبکه‌ای واقعی بات تأیید نشده است. در صورت خطا، checkpoint ناموفق جلو نمی‌رود. دادهٔ زمان قطع در Paper به‌ترتیب replay می‌شود؛ این معاملات بازسازی تاریخی‌اند، نه سفارش‌هایی که واقعاً زمان قطع ارسال شده باشند.

**Funding در polling عمومی فعلاً محاسبه نمی‌شود** و همین محدودیت روی داشبورد نمایش داده می‌شود. بک‌تست قابلیت نرخ‌های تاریخی و stress funding مستقل دارد؛ نتایج این دو حالت با هم مخلوط نشوند.

## Docker: محدودسازی دسترسی، نه گواه آماده‌بودن Live

```bash
# پس از تنظیم رمز امن در .env
# برای بررسی config از چاپ آن در لاگ عمومی پرهیز کنید؛ ممکن است رمز را شامل شود.
docker compose config --quiet
docker compose up -d --build
```

- هر دو image با UID/GID غیر-root `10001` اجرا می‌شوند.
- فایل‌ها به‌صورت انتخابی کپی می‌شوند؛ `.env`، Git، cache و داده از build context حذف شده‌اند.
- dashboard فقط `DATA_DIR` و رمز خودش را می‌گیرد؛ volume آن فقط‌خواندنی است.
- پورت میزبان پیش‌فرض فقط `127.0.0.1:8000` است. برای دسترسی بیرونی TLS proxy یا SSH tunnel لازم است.
- root filesystem فقط‌خواندنی، capabilityها حذف، `no-new-privileges`، محدودیت منابع و log rotation فعال‌اند.
- healthcheck بات هم heartbeat و هم تازگی بازار را بررسی می‌کند. `restart: unless-stopped` فقط سیاست restart پردازش است؛ وضعیت unhealthy به‌تنهایی restart یا ایمنی مالی را تضمین نمی‌کند.
- ساخت/اجرای Docker در محیط محلی این بررسی ممکن نبود؛ workflow برای build و smoke test imageها اضافه شده است.

## مهاجرت از نسخهٔ قدیمی

اگر `CONFIRM_LIVE.txt`، `risk_state.json` یا `trade_log.jsonl` در مسیر داده وجود داشته باشد، بات جدید عمداً شروع نمی‌شود.

1. قبل از توقف/جایگزینی بات قدیمی، **مستقیماً در صرافی وجود پوزیشن واقعی را بررسی و مدیریت کنید**. این نسخه نمی‌تواند حساب واقعی را بخواند، بازیابی یا ببندد.
2. از فایل‌ها و وضعیت قبلی نسخهٔ پشتیبان بگیرید؛ آن‌ها را خودکار یا بدون بررسی حذف نکنید.
3. پس از تعیین تکلیف پوزیشن‌ها، دادهٔ قدیمی را بایگانی و برای آزمایش جدید یک `DATA_DIR` جدا انتخاب کنید.
4. state قدیمی به شبیه‌سازی جدید وارد نمی‌شود؛ سرمایه/آمار آزمایش جدید نباید ادامهٔ حساب قبلی معرفی شود.

تغییر پارامترهای مالی/استراتژی با state موجود خطای fingerprint می‌دهد؛ برای آزمایش متفاوت مسیر دادهٔ جدا استفاده کنید. journal mode عمداً `DELETE` است تا داشبورد روی mount واقعاً فقط‌خواندنی، حتی پس از خروج نویسنده، بدون ساخت فایل جانبی داده را بخواند. SQLite باید روی فایل‌سیستم محلی باشد، نه NFS. برای پشتیبان‌گیری از SQLiteِ درحال اجرا از API `sqlite3.Connection.backup()` استفاده کنید؛ کپی خام فایل پایگاه هنگام transaction فعال امن نیست.

اگر قبلاً کلیدی به Git وارد شده، `.gitignore` آن را از تاریخچه پاک نمی‌کند؛ کلید باید در سرویس مربوطه باطل/تعویض و پاک‌سازی تاریخچه جداگانه بررسی شود.

## تست‌های پذیرش و امنیت

```bash
.venv/bin/python -m pytest -q
.venv/bin/python -m ruff check .
.venv/bin/python -m ruff format --check .
.venv/bin/python -m pip_audit --requirement requirements.txt --strict
```

تست‌ها شبکهٔ صرافی را مسدود می‌کنند و داده/SQLite موقت می‌سازند. بر خلاف اسکریپت تشخیصی قدیمیِ `docs/reviews/`، تست‌های `tests/` **رفتار صحیح پس از اصلاح** را بررسی می‌کنند: منع Live، auth، rollback، recovery، قفل تک‌نویسنده، کندل بسته، gap، علیت، funding، هزینه، Long/Short و خروج.

CI روی Python ۳.۱۱ و ۳.۱۲، بدون exchange secret، تست/lint/audit و build image انجام می‌دهد. نتیجهٔ اسکن وابستگی فقط آسیب‌پذیری‌های شناخته‌شدهٔ پایگاه اسکن در زمان اجرا را پوشش می‌دهد؛ ممیزی کامل برنامه، سیستم‌عامل یا حساب صرافی نیست.

برای تغییر وابستگی‌ها فایل‌های `.in` را ویرایش و lockهای دارای hash را بازتولید کنید:

```bash

.venv/bin/pip-compile --generate-hashes --allow-unsafe --no-emit-index-url --no-emit-trusted-host -o requirements-dev.txt requirements-dev.in
```

## اجرای بک‌تست

### دادهٔ خود پروژه / Codespaces — گزینهٔ ترجیحی

CSV استاندارد باید شامل این ستون‌ها باشد:

```text
time,open,high,low,close,volume,taker_buy
```

- `time`: زمان **بازشدن** کندل ساعتی به میلی‌ثانیهٔ UTC، مرتب و بدون تکرار/gap.
- `taker_buy`: حجم واقعی خرید تهاجمی در واحد دارایی پایه؛ اختیاری فقط وقتی Whale خاموش است. این ستون را با نصف حجم پُر نکنید؛ موتور پروکسی نمی‌سازد، ولی اصالت دادهٔ ارائه‌شده باید جداگانه بررسی شود.
- OHLCV باید معتبر و متناهی باشد؛ کندل آینده یا هنوز باز رد می‌شود.
- فایل funding: ستون‌های `time,rate`، یک سطر به‌ازای هر تسویهٔ واقعی. مدل فعلی BTCUSDT تسویه‌های UTC هشت‌ساعته و پوشش کامل بازه را انتظار دارد. تبدیل زمان تسویه به bucket ساعتی باید مستند شود.

```bash
.venv/bin/python -m research.backtest \
  --csv data/historical/my_candles.csv \
  --funding data/historical/my_funding.csv \
  --start 2025-01-01 --end 2026-01-01 \
  --output artifacts/my_backtest
```

`--end` انحصاری است. برای Whale فقط با دادهٔ واقعی `--whale` اضافه کنید. نبود funding باید با `--allow-missing-funding` **صریحاً** پذیرفته شود؛ نتیجه در این حالت ارزیابی کامل هزینهٔ futures نیست. دادهٔ بزرگ و لاگ حساب خصوصی را commit نکنید؛ manifest، checksum و محل ذخیرهٔ خارجی کافی است.

### بازتولید بررسی فعلی با snapshotهای عمومی واسط

دو snapshot عمومی از GitHub با commit/blob و SHA-256 ثابت استفاده شده‌اند. آن‌ها **دادهٔ تأییدشدهٔ CoinEx یا آرشیو اصلیِ احرازاصالت‌شده نیستند**. فقط داده دریافت می‌شود؛ کد مخزن ثالث اجرا نمی‌شود.

```bash
# gh برای دریافت blobهای عمومی لازم است؛ هیچ کلید صرافی لازم نیست.
.venv/bin/python -m research.run_matrix
```

خروجی:

- `data/historical/`: فایل‌های خام، canonical CSV، funding و manifest؛ خارج از Git.
- `artifacts/backtests-2026-09-20/`: برنامهٔ سناریوها، ledger معاملات، equity ساعتی و جزئیات هر اجرا؛ خارج از Git.
- `docs/reports/backtests-2026-09-20.json`: خلاصهٔ کوچک قابل مرور و شناسنامهٔ هر نتیجه.
- `docs/reports/equity-2026-09-20.svg`: نمودار سناریوهای اصلی.

قرارداد اجرا: سیگنال روی کندل بسته، ورود در Open کندل بعد با slippage، gap در قیمت Open، stop-first در برخورد مبهم stop/target، تریلینگ برای کندل بعد، خروج زمانی در Open بعد از ۱۰ کندل نگهداری و بستن اجباری انتهای داده با هزینهٔ خروج.

Funding تاریخی با نرخ ثبت‌شده و notional قیمت Open شبیه‌سازی می‌شود، نه Mark Price واقعی. order book، latency، partial fill و liquidation مدل نشده‌اند. افت سرمایهٔ گزارش‌شده بر اساس Close ساعتی است، نه بدترین افت داخل کندل. هیچ پارامتری در اجرای ماتریس برای بهترشدن نتیجه جست‌وجو یا بهینه نشده است؛ تفکیک سال‌ها جای آزمون کورِ ازپیش‌ثبت‌شده را نمی‌گیرد.

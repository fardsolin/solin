# بررسی فنی پایهٔ Solin — نسخهٔ موجود در گیت‌هاب

**تاریخ بررسی:** ۲۰۲۶-۰۹-۱۹، UTC

**مبنای بررسی:** `cb0198f88818a6969f6791b93dbf2c8cacb15f2e`

**شاخهٔ این بررسی:** `arena/01a0b9c0-solin`

> **جمع‌بندی:** تفکیک اجزای پروژه برای یک ربات تک‌بازار، ساده و قابل توسعه است؛ نیازی به بازنویسی کامل یا معماری میکروسرویس نیست. بااین‌حال، این نسخه هنوز برای معاملهٔ واقعی آماده نیست و اعداد معاملات کاغذی آن نیز پیش از اصلاح حسابداری و شبیه‌سازی اجرا، معیار قابل اتکایی برای تصمیم Live نیستند. اولویت بعدی باید «درستی داده، اجرای سفارش و بازیابی وضعیت» باشد، نه اضافه‌کردن سیگنال بیشتر.

## ۱. دامنه و محدودیت بررسی

- تمام فایل‌های متنی نسخهٔ پایه خوانده شدند: ۸ فایل Python شامل دو `__init__.py` خالی، در مجموع ۸۱۴ خط؛ همچنین README، وابستگی‌ها و تنظیمات Docker.
- نسخهٔ پایه ۱۸ فایل tracked دارد؛ ۵ فایل آن bytecode داخل `engine/__pycache__/` هستند.
- این checkout کم‌عمق (`shallow`) است و فقط یک commit در تاریخچهٔ محلی دیده می‌شود؛ این به معنی تک‌commit بودن کل مخزن نیست.
- فایل‌ها، تغییرات ذخیره‌نشده و نتایج پژوهشی داخل Codespaces در دسترس این بررسی نبودند. ممکن است بعضی موارد زیر آنجا اصلاح شده باشند؛ قبل از پیاده‌سازی اصلاحات، باید اختلاف دو نسخه بررسی شود.
- هیچ سفارش واقعی ارسال نشد و هیچ حساب یا کلید واقعی آزمایش نشد. بررسی قرارداد API از روی مستندات عمومی رسمی CoinEx انجام شد.
- ۲۶ سناریوی تشخیصی آفلاین اجرا شد. مسیرهای فایل به پوشه‌های موقت منتقل و درخواست‌های شبکهٔ کلاینت `requests` مسدود شدند. حلقهٔ بات فقط با کلاینت و ساعت شبیه‌سازی‌شده اجرا شد.
- Docker در محیط بررسی نصب نبود؛ ساخت image و اجرای واقعی Compose آزمایش نشد. Python آزمایش ۳.۱۱.۲ بود، درحالی‌که Dockerfile از ۳.۱۲ استفاده می‌کند.
- فقط این گزارش و اسکریپت بازتولید همراه آن اضافه شده‌اند؛ **هیچ منطق اجرایی، تنظیم حساب یا پارامتر معاملاتی پروژه تغییر نکرده است.**

## ۲. معماری فعلی و نقاط مثبت

```text
CoinEx public candles
        |
        v
bot.py --> StrategyEngine --> enter / hold / exit
   |                              |
   +--> RiskManager --------------+
   |                              v
   +--------------------> PaperBroker / LiveBroker --> CoinEx private API
   |
   +--> data/*.json + trade_log.jsonl --> FastAPI dashboard
```

| بخش | نقش فعلی | ارزیابی |
|---|---|---|
| `bot.py` | زمان‌بندی، دریافت داده، انتخاب بروکر و اجرای سیگنال | کوچک و قابل فهم؛ مسئولیت حسابداری و چرخهٔ سفارش بیش از حد داخل آن جمع شده است. |
| `engine/strategy.py` | شکست فشرده، زمینهٔ ۴ساعته، Whale و مدیریت خروج | جداسازی از API مناسب است؛ قرارداد زمانی داده و وضعیت معامله باید دقیق‌تر شود. |
| `engine/risk_manager.py` | تأیید انسانی، شمارش معاملات و محدودکنندهٔ ضرر روزانه | ایدهٔ دروازهٔ ایمنی درست است؛ اجرای کنترل‌ها هنوز همهٔ مسیرهای واقعی را پوشش نمی‌دهد. |
| `engine/broker.py` | رابط کاغذی و زنده | نقطهٔ مناسبی برای تست و تعویض اجراست؛ وضعیت ارسال و انجام سفارش تفکیک نشده است. |
| `engine/coinex_client.py` | REST و امضای درخواست | الگوی HMAC با دستورالعمل رسمی هم‌خوان است؛ چند فیلد قرارداد API ناقص یا اشتباه‌اند. |
| `dashboard/server.py` | خواندن گزارش و نمایش وضعیت | جدایی پردازش داشبورد از بات مفید است؛ صحت نمایش و سطح دسترسی نیازمند اصلاح‌اند. |
| Docker / Compose | اجرای دو سرویس و نگهداری فایل‌ها | شروع مناسبی برای استقرار است؛ restart به‌تنهایی معادل بازیابی ایمن معامله نیست. |

نکات مثبت قابل حفظ:

- موتور استراتژی مستقیماً سفارش صرافی نمی‌فرستد؛ همین جداسازی بازتولید خطاها را آسان کرده است.
- شروع بدون تأیید انسانی در حالت Paper و شرط حداقل معاملات، در سناریوهای کنترل درست عمل کردند.
- منطق آستانهٔ ضرر روزانه و بازنشانی روز، با ورودی‌های درست در تست واحد کار کرد.
- الگوی امضای HMAC در تست محلی با فرمول مستندات رسمی تطابق داشت؛ این جایگزین آزمایش احراز هویت واقعی نیست.
- داشبورد بدون فایل داده نیز در آزمایش درون‌پردازشی پاسخ ۲۰۰ داد.
- README محدودیت Order Flow و آزمایش‌نشدن کلاینت با کلید واقعی را مطرح کرده؛ این شفافیت ارزشمند است، هرچند بعضی ادعاهای آن با کد منطبق نیستند.

## ۳. اولویت P0 — مسدودکننده‌های استفادهٔ واقعی

در این گزارش P0 یعنی «باید پیش از فعال‌کردن معاملهٔ واقعی اصلاح شود»، نه ادعای وقوع حادثه در حساب کاربر.

### P0-1. درخواست بستن پوزیشن با قرارداد رسمی API تطابق ندارد

**محل:** `engine/coinex_client.py:103–108`

`close_position_market()` فقط `market` و `market_type` را می‌فرستد؛ اما در مستندات رسمی، `type` اجباری است. برای مقصود این تابع باید نوع سفارش مارکت مشخص باشد. در تست، بدنهٔ واقعی ساخته‌شده چنین بود:

```json
{"market": "BTCUSDT", "market_type": "FUTURES"}
```

این ناسازگاری در مسیر خروج قرار دارد، نه یک قابلیت فرعی. پاسخ سرور واقعی آزمایش نشده؛ نتیجهٔ قطعی این بررسی، نبود فیلد اجباری در کد است. [1](https://docs.coinex.com/api/v2/futures/position/http/close-position)

همچنین `get_positions()` در `engine/coinex_client.py:85–87` پارامتر اجباری `market_type` را نمی‌فرستد. فعلاً این تابع برای بازیابی وضعیت فراخوانی نمی‌شود، ولی برای افزودن reconciliation باید ابتدا اصلاح شود. [2](https://docs.coinex.com/api/v2/futures/position/http/list-pending-position)

**معیار پذیرش:** تست قرارداد درخواست‌ها با fixture مستندات؛ تعیین صریح پشتیبانی از One-way یا Hedge Mode؛ تطبیق مقدار باقی‌ماندهٔ پوزیشن پس از خروج، نه صرفاً دریافت پاسخ ارسال سفارش.

### P0-2. «ارسال سفارش» به‌جای «انجام سفارش» ثبت می‌شود

**محل:** `engine/broker.py:53–62`، `bot.py:126–150`، `engine/strategy.py:220–226`

- بروکر وضعیت `submitted` برمی‌گرداند، ولی بات بدون بررسی حجم انجام‌شده، پوزیشن محلی باز می‌کند.
- فیلد `last_fill_price` در کد با `last_filled_price` در مستندات متفاوت است؛ بنابراین پاسخ مطابق مستندات به قیمت مرجع fallback می‌کند. در تست، قیمت واقعی پاسخ `101.25` بود اما بروکر `100.0` برگرداند. [3](https://docs.coinex.com/api/v2/futures/order/http/put-order)
- حتی اصلاح نام فیلد کافی نیست: قیمت آخرین fill لزوماً میانگین اجرای کل سفارش نیست؛ حجم، قیمت میانگین، کارمزد و اجرای جزئی باید جداگانه مدل شوند.
- `_close()` قبل از تماس با بروکر، `open_trade` را `None` می‌کند. اگر خروج timeout شود یا API آن را رد کند، موتور پوزیشن را فراموش کرده است؛ این مورد با خطای شبیه‌سازی‌شده بازتولید شد.
- پاسخ اجرای خروج برای حسابداری استفاده نمی‌شود. قیمت نظری استراتژی وارد PnL می‌شود، نه اجرای تأییدشده.
- `last_seen_time` قبل از موفقیت پردازش/اجرا جلو می‌رود (`bot.py:101–105`)؛ پس خطای همان سیگنال مسیر بازیابی پایدار ندارد.

**راه‌حل معماری:** وضعیت‌های `OPENING → OPEN → CLOSING → CLOSED` و وضعیت نامعلوم/نیازمند تطبیق؛ شناسهٔ پایدار تصمیم و سفارش؛ پیگیری fill؛ نگه‌داشتن معامله تا تأیید خروج. در timeout نباید کورکورانه سفارش دیگری ارسال شود؛ ابتدا وضعیت همان سفارش و پوزیشن باید بررسی شود.

### P0-3. ری‌استارت و تغییر Paper/Live مالکیت معامله را حفظ نمی‌کنند

**محل:** `bot.py:65–89`، `engine/strategy.py:55–57`، `engine/broker.py:15–17`، `engine/risk_manager.py:36–45,74–78`

- وضعیت پوزیشن، حجم انجام‌شده، شناسهٔ سفارش، stop به‌روزشده و سرمایهٔ Paper فقط در حافظه‌اند.
- پس از ری‌استارت، شمارندهٔ معاملات ممکن است باقی بماند، ولی سرمایهٔ Paper از نو مقداردهی و موتور بدون پوزیشن ساخته می‌شود.
- هیچ تطبیقی با پوزیشن‌های واقعی حساب در شروع اجرا انجام نمی‌شود. قاعدهٔ «حداکثر یک پوزیشن» عملاً فقط در حافظهٔ همان موتور برقرار است، نه در حساب یا میان چند پردازش.
- بروکر هر دور بر اساس وجود فایل تأیید انتخاب می‌شود، نه بر اساس مالک معاملهٔ باز.
- در شبیه‌سازی، حذف فایل تأیید هنگام وجود معاملهٔ Live باعث شد خروج بعدی به `PaperBroker` برود؛ پوزیشن واقعی با چنین خروجی بسته نمی‌شود.
- حالت معکوس نیز خطر دارد: ارتقای حالت هنگام معاملهٔ Paper می‌تواند خروج فرضی را به مسیر بستن پوزیشن حساب واقعی هدایت کند.

**معیار پذیرش:** ذخیرهٔ پایدار مالک معامله (`paper/live`)، مقدار و شناسه‌ها؛ بازیابی و تطبیق پیش از اجازهٔ ورود؛ تغییر حالت فقط وقتی معاملات قبلی تعیین تکلیف شده‌اند. لغو اجازهٔ Live باید ورود جدید را متوقف کند، نه اینکه مدیریت پوزیشن Live موجود را به Paper بسپارد.

### P0-4. stop و target واقعی در صرافی ثبت نمی‌شوند

**محل:** `bot.py:97–105,126–142`، `engine/strategy.py:190–216`، `engine/broker.py:53–62`

با وجود polling پیش‌فرض ۶۰ ثانیه‌ای، منطق مدیریت پوزیشن فقط پس از شناسایی کندل بستهٔ جدیدِ یک‌ساعته اجرا می‌شود. سپس با High/Low گذشته تشخیص داده می‌شود که stop یا target لمس شده است؛ سفارش مارکت در زمان فعلی فرستاده می‌شود.

بنابراین قیمت stop که روی کندل گذشته دیده شده، قیمت اجرای تضمین‌شده نیست. در قطع برنامه/شبکه هم هیچ حفاظت سمت صرافی در این کد ثبت نشده است. تریلینگ محلی نیز سفارش حفاظتی روی صرافی را به‌روزرسانی نمی‌کند.

**معیار پذیرش:** ثبت و تأیید حفاظت سمت صرافی برای حجم واقعاً انجام‌شده؛ پایش شکست ثبت حفاظت؛ مدیریت مستقل پوزیشن‌های باز؛ ثبت قیمت و هزینهٔ واقعی اجرا. حتی stop سمت صرافی هم قیمت دقیق یا سقف قطعی زیان را در گپ و نقدشوندگی پایین تضمین نمی‌کند.

### P0-5. مبنای اندازهٔ سفارش و PnL قابل اتکا نیست

**محل:** `engine/risk_manager.py:25–41`، `bot.py:119–149`، `engine/broker.py:46–51`

1. `RISK_PER_TRADE_PCT` از محیط خوانده می‌شود اما در state اولیه قرار نمی‌گیرد؛ بات مقدار را از `risk.state` می‌خواند و در حالت عادی همیشه به `0.01` برمی‌گردد. با تنظیم ۲٪، سرمایهٔ ۱۰٬۰۰۰ و فاصلهٔ stop برابر ۱۰، اندازهٔ سفارش **۱۰** شد، نه **۲۰**.
2. حسابداری خروج مستقل از اندازهٔ واقعی معامله، همیشه ضریب ثابت `0.01` دارد. حتی با اصلاح دستی مقدار ریسک در state، سود اندازهٔ ۲۰ واحد در حرکت ۱۰۰→۱۱۰ به‌جای ۲۰۰، برابر ۱۰۰ ثبت شد.
3. برای Short قرارداد خطی USDT، فرمول بازده `entry / exit - 1` درست نیست. مثلاً ورود ۱۰۰ و خروج ۹۰، بازده قیمتی ۱۰٪ است، نه ۱۱.۱۱٪. باید PnL از مقدار واقعی و اختلاف قیمت محاسبه شود.
4. محدودکردن مصنوعی R به بازهٔ `[-1.5, 10]` نباید زیان یا سود ثبت‌شدهٔ حساب واقعی را جایگزین کند؛ این کار می‌تواند معیار ضرر روزانه را تحریف کند.
5. کارمزد، funding، slippage، حجم partial fill، قواعد حداقل/گام مقدار سفارش و محدودیت margin در حسابداری/اندازه‌گذاری مدل نشده‌اند.
6. `available + frozen` لزوماً equity حساب نیست. مستندات، `account_balance` و `unrealized_pnl` را جدا تعریف می‌کنند و `available` را فیلدی در مسیر حذف معرفی کرده‌اند. [4](https://docs.coinex.com/api/v2/assets/balance/http/get-futures-balance)
7. شکست تنظیم leverage فقط چاپ می‌شود و اجرا ادامه پیدا می‌کند (`engine/broker.py:41–44`)، درحالی‌که تنظیم مؤثر حساب تأیید نشده است.

**پیشنهاد:** ledger مستقل Paper و Live، محاسبات مقدار و پول با دقت مشخص، تعریف صریح equity و مبنای ضرر روزانه. برای قرارداد خطی و خروج کامل، پایهٔ محاسبه باید تقریباً چنین باشد؛ معاملات چند fill یا خروج جزئی به تجمیع جداگانه نیاز دارند:

```text
realized_pnl = direction_sign * filled_quantity * (exit_avg - entry_avg)
               - trading_fees + signed_funding_cashflows
```

ریسک هدف با ریسک تحقق‌یافته یکی نیست؛ گزارش باید هر دو را نشان بدهد.

## ۴. اولویت P1 — درستی استراتژی، داده و پایش

### P1-1. خروج زمانی پس از پرشدن بافر از کار می‌افتد

**محل:** `engine/strategy.py:64–72,187–188,203–216`

بافر در ۱۰۰۰ کندل محدود می‌شود، اما `entry_bar_index` با حذف کندل‌های قدیمی اصلاح نمی‌شود. برای معامله‌ای که در طول بافر ۱۰۰۰ باز شده، `len(candles) - 1` همیشه ۹۹۹ است و تعداد کندل نگهداری صفر می‌ماند. آزمایش با ۱۰ کندل آرام:

- شروع با ۸۰۰ کندل: خروج `time-exit` انجام شد.
- شروع با ۱۰۰۰ کندل: نتیجه همچنان `hold` و `bars_held=0` بود.

**اصلاح پیشنهادی:** شمارهٔ ترتیبی سراسری کندل یا شمارندهٔ پایدار معامله؛ مدت نگهداری نباید به موقعیت سطر در بافر قابل‌برش وابسته باشد.

### P1-2. کندل ناقص warmup اصلاح نمی‌شود و gapها بازیابی نمی‌شوند

**محل:** `bot.py:60–77,97–105`

تمام پاسخ تاریخچه، بدون تشخیص بسته‌شدن، وارد موتور می‌شود و زمان آخرین سطر در `last_seen_time` قرار می‌گیرد. اگر آخرین سطر کندل جاری باشد، پس از بسته‌شدن شرط `>` برقرار نیست؛ همان مقدار ناقص در تاریخچه می‌ماند.

در بازتولید، Close اولیهٔ `111` حتی پس از دریافت نسخهٔ بسته با Close برابر `222` در موتور باقی ماند. فقط کندل بعدی پردازش شد.

همچنین هر دور فقط `df_new.iloc[-2]` اضافه می‌شود. پس از وقفه، حتی کندل‌های قدیمی‌تر موجود در همان پاسخ هم نادیده گرفته می‌شوند. تست وقفه، فاصلهٔ سه‌ساعته بین دو سطر متوالی تاریخچه ایجاد کرد.

**اصلاح پیشنهادی:** قرارداد صریح `open_time/close_time` و UTC؛ حذف partial در warmup؛ upsert بر اساس بازار/بازه/زمان؛ backfill مرتب تمام فاصله‌ها؛ اعتبارسنجی OHLCV، تکرار و تازگی داده. بعد از وقفه، بازیابی داده نباید به اجرای سفارش ورودِ سیگنال‌های منقضی‌شده منجر شود. مرزبندی کندل‌های ۴ساعته نیز باید با همین قرارداد زمانی تست شود.

### P1-3. سیگنال Whale در ورودی فعلی همیشه خاموش است

**محل:** `bot.py:50–55` و `engine/strategy.py:94–99`

```text
TakerBuyBase = Volume * 0.5
Delta       = 2 * TakerBuyBase - Volume = 0
WhaleBuy    requires Delta > 0
WhaleSell   requires Delta < 0
```

این صرفاً یک تخمین ضعیف‌تر از Order Flow نیست؛ با داده‌های عادی معتبر، هر دو سیگنال را حذف می‌کند. در تست ۱۰۰۰ کندل با جهش حجم هزاربرابری نیز هیچ‌کدام فعال نشدند. این وضعیت هم Paper و هم Live همین برنامه را شامل می‌شود.

**تصمیم لازم:** یا فید معتبر و هم‌تراز Order Flow اضافه شود، یا قابلیت Whale صریحاً غیرفعال و استراتژی باقی‌مانده جداگانه بک‌تست شود. نباید نتایج ترکیب دو سیگنال به نسخه‌ای که یکی از آن‌ها را ندارد نسبت داده شوند.

### P1-4. تریلینگ از ترتیب نامعلوم رویدادهای داخل کندل استفاده می‌کند

**محل:** `engine/strategy.py:193–213`

ابتدا stop بر اساس بهترین High/Low همان کندل بالا می‌آید؛ سپس Low/High همان کندل برای برخورد با stop جدید بررسی می‌شود. OHLC ترتیب این دو اتفاق را مشخص نمی‌کند.

برای Long با ورود ۱۰۰، stop اولیهٔ ۹۵، High برابر ۱۰۱ و Low برابر ۹۴، موتور خروج سوددهٔ `100.9` ثبت کرد. اما اگر Low ابتدا رخ داده باشد، stop اولیه پیش از شکل‌گیری آن سود لمس شده است. پس این مثال **ابهام ترتیب و امکان خوش‌بینی شبیه‌سازی** را ثابت می‌کند، نه اینکه ترتیب واقعی بازار همیشه مشخص بوده است.

**اصلاح پیشنهادی:** دادهٔ ریزتر برای اجرا یا قرارداد محافظه‌کارانهٔ روشن دربارهٔ ترتیب داخل کندل؛ همسان‌سازی آن بین backtest، Paper و Live. قانون «stop جدید از کندل بعد معتبر است» نیز می‌تواند یک قرارداد قابل‌آزمایش باشد، ولی رفتار استراتژی را تغییر می‌دهد و نیازمند ارزیابی مجدد است.

### P1-5. محدودکنندهٔ روزانه و آمار Paper مرز مسئولیت صحیح ندارند

**محل:** `bot.py:91–95,145`، `engine/risk_manager.py:54–62`

- وقتی breaker فعال است، کل دریافت و مدیریت کندل با `continue` کنار گذاشته می‌شود. اگر پوزیشنی موجود باشد، مدیریت آن هم متوقف می‌شود؛ این حالت با state تزریق‌شده آزمایش شد. در مسیر عادی فعلی، breaker عموماً بعد از بسته‌شدن معامله فعال می‌شود، پس این یافته یک شرط خطرناک در طراحی است، نه ادعای وقوع دائمی آن.
- `record_closed_trade()` ورودی mode ندارد و خروج Live نیز `paper_trades_completed` را زیاد می‌کند. این به‌خودی‌خود اثبات دورزدن شرط اولیهٔ ۵۰ معامله نیست، ولی آمار Paper را پس از Live آلوده می‌کند.
- PnL روزانه از اعداد نظری بند P0-5 تغذیه می‌شود و زیان تحقق‌نیافته را در نظر نمی‌گیرد.
- روز ریسک با `date.today()` محلی و دادهٔ بازار با UTC تعریف شده؛ سیاست مرز روز باید صریح و یکسان شود.

**اصل پیشنهادی:** مجوز «ورود جدید» از وظیفهٔ «مدیریت و کاهش ریسک پوزیشن موجود» جدا باشد؛ شمارنده و ledger هر mode نیز مستقل بماند.

### P1-6. داشبورد می‌تواند وضعیت ریسک را اشتباه نشان بدهد

**محل:** `dashboard/server.py:45–69,121–135`، `engine/risk_manager.py:80–90`

رابط از `d.risk_state` استفاده می‌کند، درحالی‌که بعضی فیلدهای نمایشی فقط در heartbeat تولید می‌شوند:

| مورد | دادهٔ موجود | نتیجهٔ فعلی قالب |
|---|---|---|
| PnL روزانه | در state کسری مانند `-0.03`، در heartbeat درصد `-3.0` | state مستقیم با `%` نمایش داده می‌شود؛ ۳٪ زیان به‌شکل `-0.03%` دیده می‌شود. |
| Circuit Breaker | در heartbeat وجود دارد؛ در state اولیه وجود ندارد | شرط UI معمولاً آن را خاموش نشان می‌دهد، حتی وقتی heartbeat فعال است. |
| حداقل معاملات | `paper_trades_required` در heartbeat | قالب از state می‌خواند و `--` نشان می‌دهد. |
| سلامت بات | heartbeat خطا هم timestamp تازه دارد | فقط تازگی بررسی می‌شود؛ خطای مداوم ممکن است «آنلاین» نشان داده شود. |

همچنین منحنی سرمایه و نرخ برد Paper/Live با هم مخلوط می‌شوند. در جدول رخداد خروج نیز وجود `entry_price` باعث می‌شود قیمت ورود بر قیمت خروج اولویت داشته باشد (`dashboard/server.py:155`).

**اصلاح پیشنهادی:** یک schema واحد برای status، واحدهای مشخص، تفکیک mode، نمایش پوزیشن و exposure، و تمایز سلامت پردازش، سلامت اجرای سفارش و تازگی بازار.

### P1-7. نوشتن/خواندن JSON اتمیک نیست

**محل:** `engine/risk_manager.py:36–45`، `bot.py:38–41`، `dashboard/server.py:38–42`

خواندن هم‌زمان با نوشتن یا توقف وسط نوشتن می‌تواند JSON ناقص ایجاد کند. heartbeat ناقص در تست باعث HTTP 500 شد؛ خرابی `risk_state.json` نیز مسیر بازیابی تعریف‌شده ندارد.

**اصلاح کوتاه‌مدت:** نوشتن در فایل موقت و replace اتمیک، مدیریت خطای خواندن و نسخهٔ سالم قبلی. برای دفتر معاملات و وضعیت سفارش، تراکنش پایدار مناسب‌تر از چند فایل مستقل است.

## ۵. پایهٔ گیت‌هاب، امنیت و استقرار

### موارد لازم پیش از انتشار همراه با کلید واقعی

- `.env.example` وجود ندارد، با اینکه README دستور `cp .env.example .env` دارد؛ نصب مستندشده از همان مرحله ناقص است.
- `.gitignore` وجود ندارد، برخلاف ادعای README دربارهٔ محافظت از `.env`.
- `.dockerignore` وجود ندارد و هر دو Dockerfile از `COPY . .` استفاده می‌کنند؛ اگر `.env` در build context ساخته شود، ممکن است داخل هر دو image کپی شود. در snapshot بررسی‌شده فایل `.env` موجود نبود؛ **این گزارش ادعای نشت کلید موجود ندارد.**
- سرویس داشبورد در Compose تمام `.env` را می‌گیرد، با اینکه به کلید صرافی نیاز ندارد؛ volume داده هم برای آن read-write است. باید دسترسی حداقلی و ترجیحاً volume فقط‌خواندنی داشته باشد.
- داشبورد احراز هویت ندارد و Compose پورت ۸۰۰۰ را منتشر می‌کند. در استقرار عمومی، اطلاعات مالی بدون کنترل دسترسی قابل مشاهده‌اند؛ reverse proxy با TLS و احراز هویت یا دسترسی شبکهٔ خصوصی لازم است.
- دستور ساخت `data/CONFIRM_LIVE.txt` روی میزبان با named volume موجود در Compose یکسان نیست. فایل میزبان خودکار وارد `bot_data:/app/data` نمی‌شود؛ مسیر عملیات مدیریتی باید با استقرار واقعی سازگار باشد.

### موارد نگهداری و قابلیت بازتولید

- پنج فایل `.pyc` باید از نسخه‌بندی حذف و cacheها، محیط مجازی، `.env` و دادهٔ عملیاتی از Git/build context مستثنا شوند؛ خود داده‌ها نباید بدون بررسی پاک شوند.
- وابستگی‌ها فقط حد پایین `>=` دارند؛ buildهای دو روز مختلف لزوماً یکسان نیستند. lock، نسخهٔ Python مشخص و تفکیک وابستگی آزمون/اجرا لازم است.
- `python-dotenv` نصب می‌شود، اما `load_dotenv()` فراخوانی نمی‌شود. Compose متغیرها را تزریق می‌کند؛ اجرای مستقیم `python bot.py` صرف وجود `.env` آن را نمی‌خواند.
- پیکربندی نوع‌دار با اعتبارسنجی دامنه، واحد درصد، mode و leverage لازم است. تنظیم نامعتبر یا نامعلوم در Live باید جلوی ورود جدید را بگیرد.
- تست پذیرش، CI، healthcheck، راهنمای بازیابی حادثه و تنظیمات بازتولیدپذیر Codespaces در این snapshot وجود ندارند.
- داشبورد هر ۱۵ ثانیه کل JSONL و منحنی سرمایه را می‌خواند/ارسال می‌کند؛ برای اجرای طولانی باید pagination، خلاصه‌سازی و سیاست نگهداری اضافه شود.
- containerها کاربر غیر-root تعریف نکرده‌اند؛ برای استقرار جدی باید مجوز فایل، محدودیت منابع، log rotation و پشتیبان‌گیری هم مشخص شوند.

## ۶. اعتبار نتایج پژوهشی

README به PF حدود ۱.۷۹، اعتبارسنجی ۲۰۲۰–۲۰۲۶ و عملکرد مثبت خارج از نمونه اشاره دارد. در این نسخه، runner بک‌تست، داده یا manifest آن، دفتر معاملات خروجی و پیکربندی آزمایش موجود نیست؛ بنابراین این اعداد **از این مخزن قابل تأیید یا بازتولید نیستند**. این نتیجه به معنی رد پژوهش احتمالی داخل Codespaces نیست.

برای قابل اتکا شدن این ادعاها، همراه کد پژوهش باید موارد زیر ثبت شوند:

1. نسخه و منبع داده، timezone، معنای زمان کندل و checksum؛ دادهٔ حجیم می‌تواند خارج Git بماند.
2. بازه‌های train/validation/test و روش walk-forward، بدون تنظیم پارامتر روی test.
3. قرارداد اجرای سفارش، هزینه، funding، slippage و ترتیب رخداد داخل کندل.
4. پارامترها، نسخهٔ کد، seed در صورت وجود تصادف، و ledger قابل بررسی.
5. مقایسهٔ نسخهٔ دارای Order Flow واقعی با نسخهٔ بدون Whale؛ نه استفادهٔ مشترک از یک عدد PF.
6. آزمون همسانی سیگنال در backtest و پردازش bar-by-bar برای داده و پیکربندی یکسان.

۵۰ معاملهٔ Paper یک دروازهٔ عملیاتی است، نه به‌تنهایی گواه سودآوری یا اعتبار آماری. README دربارهٔ تناسب افت سرمایه با اهرم هم باید به مدل دقیق مقدار پوزیشن و margin متکی باشد؛ در اندازه‌گذاری با ریسک ثابت، صرف تغییر leverage الزاماً بازده و افت سرمایه را خطی ضرب نمی‌کند.

## ۷. مسیر پیشنهادی رشد پروژه

### مرحلهٔ صفر: تطبیق با Codespaces و تثبیت مبنا

- فایل‌های منبع، تست‌ها و پیکربندی پژوهشی جدید را بدون `.env`، کلیدها، لاگ خصوصی یا دیتاست حجیم به همین مبنای کاری برسانیم.
- diff نسخه‌ها را بررسی و برای هر یافته مشخص کنیم: هنوز موجود، آنجا اصلاح‌شده، یا نیازمند آزمایش بیشتر.
- README، مثال تنظیمات، ignoreها و وابستگی‌های قفل‌شده را با واقعیت یکسان کنیم.

**خروجی قابل پذیرش:** یک checkout تمیز روی Python هدف، با دستور نصب و اجرای Paper مستند و تکرارپذیر؛ بدون نیاز به هیچ کلید واقعی.

### مرحلهٔ یک: هستهٔ قابل اعتماد Paper

- اصلاح زمان کندل و backfill، خروج زمانی، تصمیم دربارهٔ Whale و مدل محافظه‌کارانهٔ اجرای داخل کندل.
- مدل مشترک `Candle / Signal / Order / Fill / Position / AccountSnapshot`.
- ledger مبتنی بر مقدار واقعی، هزینه‌ها و وضعیت پایدار؛ بازیابی Paper پس از ری‌استارت بدون تغییر equity/position.
- تبدیل یافته‌های این گزارش به تست‌هایی که **رفتار مطلوب** را assert کنند، نه تست‌های تأیید وجود باگ.

**خروجی قابل پذیرش:** replay یک داده و تنظیم ثابت، سیگنال و ledger یکسان بسازد؛ restart، gap و دادهٔ تکراری خروجی را خراب نکنند؛ محدودکنندهٔ ضرر از اعداد درست تغذیه شود.

### مرحلهٔ دو: لایهٔ اجرای ایمن و تطبیق حساب

- اصلاح قراردادهای API؛ تست fixture برای ACK، partial fill، reject، timeout و نرخ درخواست.
- ماشین وضعیت سفارش، idempotency، reconciliation در شروع و حین اجرا، حفاظت سمت صرافی و کنترل مالکیت پوزیشن.
- محدودکردن حالت‌های حساب پشتیبانی‌شده و جلوگیری از کار هم‌زمان دو نویسنده/بات برای یک حساب و بازار.
- ورودهای جدید هنگام خطا یا دادهٔ کهنه متوقف شوند، ولی مدیریت پوزیشن موجود ادامه داشته باشد.

**خروجی قابل پذیرش:** در آزمایش تزریق خطا، هیچ پوزیشن فراموش‌شده یا سفارش تکراری ایجاد نشود؛ تغییر mode نتواند بروکر مالک معامله را عوض کند. آزمایش حساب واقعی فقط در مرحله‌ای جدا، با مجوز صریح و پس از عبور از این معیارها انجام شود.

### مرحلهٔ سه: مشاهده‌پذیری و اعتبارسنجی عملکرد

- API وضعیت صحیح، نمایش mode جدا، exposure و قیمت/کارمزد واقعی.
- هشدار قطع داده، خطای سفارش، حفاظت ناموفق و مغایرت حساب.
- backtest و replay قابل بازتولید؛ سپس دورهٔ Paper با همان منطق اجرا و هزینه.
- CI بدون secret: lint، تست واحد و قرارداد، تست recovery و build Docker روی Python هدف.

**خروجی قابل پذیرش:** هم درستی مهندسی و هم نتایج پژوهشی قابل توضیح و بازتولید باشند؛ هیچ ادعای سوددهی صرفاً از سبز بودن تست‌ها نتیجه نشود.

## ۸. معماری هدفِ متناسب با اندازهٔ پروژه

همین ساختار ماژولار کافی است؛ پیشنهاد فعلی مهاجرت به میکروسرویس، Kafka یا زیرساخت سنگین نیست:

```text
MarketDataAdapter -> ClosedCandleStore -> Strategy -> Signal
                                              |
                                              v
                              RiskPolicy (new-entry permission)
                                              |
                                              v
                         ExecutionService / Order State Machine
                              |                         |
                      Paper Adapter               CoinEx Adapter
                              |                         |
                              +----> Fill / Ledger <----+
                                         |
                               Position Repository
                                         |
                              Reconciler + Monitoring
                                         |
                                  Read-only Dashboard
```

برای یک VPS و یک نویسنده، SQLite با تراکنش و WAL می‌تواند نقطهٔ شروع مناسبی برای وضعیت و ledger باشد؛ JSONL برای audit/export باقی بماند. انتخاب PostgreSQL زمانی توجیه دارد که نیاز واقعی هم‌زمانی/چند نمونه وجود داشته باشد.

اصول غیرقابل مذاکرهٔ طراحی:

- دادهٔ تأییدنشده، کهنه یا دارای gap اجازهٔ ورود جدید نمی‌دهد.
- تأیید ارسال سفارش، تأیید انجام آن نیست.
- پوزیشن تا تأیید خروج از حساب یا تطبیق معتبر، باز/درحال‌بسته‌شدن محسوب می‌شود.
- حالت Paper/Live متعلق به معامله است، نه صرفاً تنظیم لحظه‌ای حلقه.
- توقف ورود، وظیفهٔ حفاظت و کاهش ریسک را متوقف نمی‌کند.
- PnL واقعی از fill و هزینه محاسبه می‌شود، نه از قیمت نظری سیگنال.

## ۱۰. منابع رسمی بررسی قرارداد API

این صفحات در تاریخ بررسی خوانده شدند؛ قراردادهای API ممکن است تغییر کنند و پیش از ادغام Live باید دوباره تطبیق داده شوند.

1. [1](https://docs.coinex.com/api/v2/futures/position/http/close-position) — فیلدهای اجباری بستن پوزیشن و تفاوت حالت‌های حساب.
2. [2](https://docs.coinex.com/api/v2/futures/position/http/list-pending-position) — پارامتر `market_type` و اطلاعات پوزیشن موجود.
3. [3](https://docs.coinex.com/api/v2/futures/order/http/put-order) — وضعیت حجم سفارش و فیلد `last_filled_price`.
4. [4](https://docs.coinex.com/api/v2/assets/balance/http/get-futures-balance) — تعریف balance، margin، available و unrealized PnL.
5. [5](https://docs.coinex.com/api/v2/authorization) — فرمول امضای HMAC و هدرها.
6. [6](https://docs.coinex.com/api/v2/futures/market/http/list-market-kline) — ساختار کندل و واحد میلی‌ثانیهٔ timestamp؛ تبدیل میلی‌ثانیه در `klines_to_df()` با این قرارداد سازگار است.
